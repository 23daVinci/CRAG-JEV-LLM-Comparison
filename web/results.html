jev-bench Minimal-infrastructure A/B benchmark of a CRAG-style retrieval workflow Held-out test set, n = 1,000 (head-to-head n = 19)

How much does swapping LLM decision nodes for Jev save? In a CRAG-style workflow: far less latency and cost, with minimal tuning and good accuracy.

One LangGraph workflow; its classification-style calls (is this passage relevant, is the evidence sufficient, should it retry) go to an LLM or to Jev, TypeSafe AI's model that returns typed probabilities instead of generated text. Jev ran all 1,000 test questions; Groq's free tier (about 30 queries a day) capped the head-to-head at 19.

Hard multi-hop benchmark
2 of 10 paragraphs, both required

HotpotQA distractor, dev set: every question rated “hard”. Bridge questions (~71%) reach the second gold paragraph only via an entity named in the first; the rest (~29%) are comparisons. Scored against gold supporting facts, no LLM judge.

Minimal infrastructure
CPU-only machine, no GPU

Retrieval ranks the 10 paragraphs with nomic-embed-text (137M parameters, 274 MB) via Ollama on CPU. No vector database, no fine-tuning, no reranker. Jev and the LLM are called as hosted APIs.

Minimal tuning
2 thresholds tuned, 3 at defaults

Relevance 0.40 and injection 0.50, set on 80 train + 10 validation questions. Evidence, contradiction and sufficiency stay at the vendor's defaults. Nothing re-tuned for the 1,000 test questions; no fine-tuning, and both backends get identical prompt wording.

Why it's apples to apples

Same compiled LangGraph graph, same selected-document-set task, two interchangeable decision backends.

  1. retrieve
  2. →
  3. screen
  4. →
  5. sufficiency
  6. →
  7. decide_retry

Decision node, answered by whichever backend is plugged in. Identical node/edge topology for both is asserted by a test, not by convention.

Injection guard

Planted prompt-injection probes, ground truth exact by construction. Held-out set of 200 probes: 100 matched clean/injected pairs.

Jev 1.00 / 1.00 / 1.00 precision / recall / accuracy

Jev flagged every injected probe and no clean one. qwen3.8-27b was not run on this set (token quota), so this is a Jev-only result with no comparison implied.

1,100 questions, four disjoint splits

Only the 80 train and 10 val questions were used to set the two tuned thresholds (setup, above). The 1,000 test questions are disjoint from both, and from a 10-question pilot, and were never used for tuning. Jev completed all 1,000 with 0 failures.

Objective labels

Output under test is the selected document set, scored per query against HotpotQA's own gold supporting facts. No LLM judge, no generation step.

Shared retrieval, frozen pool

The CPU embedding retrieve step is identical for both backends; only the decision nodes differ. Real qwen3.8-27b and Jev API calls against a frozen document pool, hashed before and after each query.

Small n, stated plainly

The head-to-head is 19 random test queries (20 run, 1 lost to a Groq request timeout), so only the Jev-alone number is tightly measured. It supersedes the 10-query pilot (qwen3.8-27b 0.677 vs. Jev 0.533), which was too small to conclude anything.
