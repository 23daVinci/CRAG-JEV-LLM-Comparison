# eval/dataset.jsonl — data card

## Source

[HotpotQA](https://hotpotqa.github.io/) dev set, **distractor setting**
(`hotpot_dev_distractor_v1.json`), Yang et al. 2018, Stanford NLP.

derived from it (including `eval/injection_probes.jsonl` below, since its base passages come from

the rest of the repo.

## What's in this file

A frozen slice of 1,100 questions (781 bridge + 319 comparison): a 100-question tuning base (71
bridge + 29 comparison: train, val, pilot) plus a 1,000-question held-out test set (710 bridge + 290
comparison, same 71:29 ratio), all selected with a
fixed seed (20260915) from the full ~7.4k-question dev-distractor set (5,918 bridge + 1,487
comparison available — plenty of headroom). The full dev set is entirely "hard" difficulty —
HotpotQA's easy/medium questions exist only in the train split, not dev — so difficulty is not a
selection axis here. (Raised from an original 45-question slice — 32 bridge + 13 comparison, same
71:29 ratio — for more statistical headroom in threshold tuning; see `eval/splits.json` below.)

Each line is one JSON record:

```json
{
  "id": "<HotpotQA _id>",
  "question": "...",
  "answer": "...",
  "type": "bridge" | "comparison",
  "level": "hard",
  "context": {"<Wikipedia title>": "<paragraph text>", ...},   // all 10 distractor-setting docs
  "gold_titles": ["<title>", ...]                                 // 2 titles, from supporting_facts
}
```

`gold_titles` is the ground truth this project uses for quality parity: selected-document-set
precision/recall/F1 against `gold_titles`, not a human or LLM-judged label. `answer` is kept for
reference but is not consumed anywhere in this pipeline — there is no generation step (see the
project's plan/README for why).

## Curation method

`scripts/curate_eval_set.py`, run against a local copy of `hotpot_dev_distractor_v1.json`
(not committed — see `.gitignore`; the official host is
`http://curtis.ml.cmu.edu/datasets/hotpot/hotpot_dev_distractor_v1.json`, mirrored on Hugging Face
at `RAGLAB/data`). Selection: shuffle bridge and comparison questions separately under a fixed seed,
take the first 71 and 29 respectively, interleave (`scripts/curate_eval_set.py`). The 1,000 test
questions are then appended by `scripts/add_test_set.py`, drawn from the same shuffled order but
excluding every question already in the base — so train, val, pilot and test are disjoint by
construction (also checked in `tests/unit/test_probe_split_consistency.py`). No filtering by content,
length, or difficulty beyond type — the goal is a representative, not a cherry-picked, slice.

## eval/injection_probes.jsonl

A separate synthetic test set for the injection-screening guard (plan milestone 6). Prompt
injection isn't organic to HotpotQA, so this ground truth is constructed, not judged: 40 distractor
passages (never gold documents) are sampled from `dataset.jsonl` under the same fixed seed, and
each produces a matched pair — one unmodified ("clean") copy and one with a known injection string
appended ("injected") — so the two differ only in the presence of the injection text, not in topic
or length. Generated by `scripts/generate_injection_probes.py`. Each line:

```json
{
  "id": "probe-NNN-clean" | "probe-NNN-injected",
  "query_id": "<source dataset.jsonl record id>",
  "query": "...",
  "title": "<source passage title>",
  "text": "...",
  "is_injection": true | false
}
```

Scored via `jev-bench injection-eval` / `bench/injection_eval.py`'s `evaluate_injection_guard`.
Split by `query_id` via `eval/splits.json` below: 31 train / 4 val / 5 pilot / 100 test pairs (the
100 test pairs come from test-set queries only, with a separate rng stream, and are appended after
the 40 base pairs so the train/val probes the injection threshold was tuned on are byte-identical to
before). Val is thin in
absolute terms, but injection detection has consistently been an easily-separable signal in this
project (both backends reaching precision/recall 1.00 even at similarly small val sizes previously)
— `N_SAMPLES` wasn't raised further since there's no evidence yet that it needs to be.

## eval/splits.json

A deterministic assignment of each of `dataset.jsonl`'s 1,100 query IDs to one of four splits:

| Split | Queries | Role |
|---|---|---|
| `train` | 80 | Jev's thresholds are *searched* here (precision-recall sweep) |
| `val` | 10 | confirms the picked threshold out-of-sample, no re-search |
| `pilot` | 10 | the original small held-out set; scored and published (n=10) before the large test set existed |
| `test` | 1,000 | the headline evaluation: fresh questions, scored with the thresholds *as tuned on train/val*, i.e. minimal further tuning |

train/val/pilot (the 100 base queries, 80/10/10, stratified by `type`: 57/7/7 bridge, 23/3/3
comparison) come from `scripts/split_eval_queries.py`; `test` comes from `scripts/add_test_set.py`
(710 bridge + 290 comparison, disjoint from all of the above by id and by question text).
`injection_probes.jsonl` records inherit their split from their `query_id` here, not an independent
assignment, so both halves of a clean/injected pair always land together.

The `pilot` split exists because its results had already been looked at when the large test set was
designed; keeping it separate from `test` means the 1,000-question evaluation is on questions nobody
(including whoever picked the thresholds) has seen results for. At 1,000 queries one query moves a
mean F1 by 0.001, so the test split can support much tighter conclusions than the pilot's n=10 — a
bootstrap CI over queries is still reported, never a bare point estimate.

Note: a small number of HotpotQA records ship with fewer than 10 context paragraphs (13 of the 1,000
test records, 2 of the 100 base records; the source file has no duplicate titles and every gold
title is present) — that is a property of the dataset, not a curation artifact.
